# 能力对照：NetHub vs Proxifier（p） vs gost

> 结论先行：**我们不是"功能更少的 Proxifier"，而是另一个物种** —— 它按"哪个程序"决定走不走代理，
> 我们按"访问哪个目标"决定。这个差别让我们在客户现场更省心（装完不用教人配规则），
> 但也确实在几个方向上有真缺口，下面分「它强」「我们强」「真缺口」「明确不做」四块讲。
>
> 调研基线：Proxifier Windows v4.14（2025-04-23，官方 changelog 无 Windows v5）；
> gost v3.3.0（2026-08-30）。来源见每条的链接。

---

## 一、逐维度对照

| 维度 | Proxifier | gost v3 | NetHub 现状 |
|---|---|---|---|
| **拦截方式** | WFP callout 驱动（可拦底层调用，含 Store/WSL） | Windows 上**不能**做透明代理（red/redu 依赖 Linux iptables/tproxy） | WinDivert 内核驱动 + 用户态改包（TCP/IPv4） |
| **规则匹配维度** | 进程名/路径、目标主机（支持通配符）、目标 IP/网段、端口范围、时间 | bypass 规则：域名/IP/正则（**不做域名→CIDR 联动**） | 目标 IP/CIDR + 端口（单值/范围/列表） |
| **规则动作** | 走代理 / 直连 / 阻断 | 转/不转（bypass） | 走指定链 / 直连 / 阻断（回 RST，应用立刻被拒） |
| **规则顺序语义** | 自上而下命中即止 + 手动/自动排序 | 优先 bypass | 自上而下命中即止 + 影子检测 + "按最具体优先"一键排序 |
| **上游协议** | SOCKS4/5、HTTP/HTTPS、SOCKS over HTTPS | 入口 21 种 / 出口 11 种协议 × 传输 27 种（ws/mws/kcp/quic/h2/grpc/ss/sshd/ohttp/otls/utls…） | SOCKS4/4a/5(socks5h)、+TLS/+mTLS、HTTP/HTTPS CONNECT（Basic 认证） |
| **多上游/负载均衡** | 代理链（多跳）+ 规则可指定不同代理 | hops 多跳；selector：round/rand/fifo/hash/**parallel 竞速**；**weight 加权**；backup 标记；maxFails/failTimeout | **单跳多上游**：failover（默认）/round/random；按健康度动态排序 |
| **健康检查** | proxy checker 独立工具 + 自动切换 | 主动 probe（tcp/http/cmd/icmp）+ 被动失败标记 + failCodes | 主动：TCP[+TLS] 握手探测（间隔可配）；被动：真实连接成败也计入 |
| **超时控制** | 各级超时可配 | 各层可配 | 单次超时（默认 5s）+ 总预算（默认 10s），失败立刻换下一条 |
| **UDP** | 不处理（只 TCP/UDP 都转但不做隧道？实际只转发 TCP 类） | 全面支持（UDP 转发、SOCKS5 UDP ASSOCIATE、relay 同时承载 TCP+UDP、ssu、rudp） | **只拦 TCP**（内网业务全是 TCP） |
| **DNS** | 远程解析三模式（Do NOT/ONLY 名单）、**假 IP 子网**、DNS 泄漏防护、DNS 走代理 | dns handler 代理入站；分流器不解析域名 | hosts 托管（写标记区块）+ Clash 共存/DNS 泄漏面检测 |
| **观测** | 连接列表（进程/PID/目标/字节/耗时）、流量 dump（.dmp 抓包）、log 导出 | metrics(Prometheus)、observer 插件、API、Web UI、限速/配额 | 连接列表（目标/动作/链/时长/**双向字节**/包数/状态/错误）、日志文件+界面、累计与按链统计 |
| **诊断** | 内置 log level、proxy checker、连接环路检测 | 日志级别、profiling | **一键诊断（四项：体检/巡检/链路自检/Clash 共存）**、规则模拟器、诊断包（脱敏配置+日志+报告） |
| **配置** | .ppx 文件 + **企业批量下发**（silent-load / Default.ppx 全机强制 / 远程自动更新）+ profile 加密 | YAML/JSON、热重载（SIGHUP/`-R`/API）、插件体系 | config.yaml + 自动备份（20 份）+ 回滚 + 导出配置/说明 + **客户装机包** |
| **部署** | 服务模式 + Service Manager（配置导入服务需重启服务）+ 便携版 | Windows 服务只有 `sc create`；无 install/uninstall 文档 | **headless + 一键安装/启停/卸载 Windows 服务**、开机自启（计划任务最高权限）、单实例、托盘 |
| **界面** | 原生 Win32，简单 | 无（命令行/配置） | Wails + WebView2，中文界面、深/浅色 |

## 二、我们比它们强的地方（别丢）

1. **规则按目标、不按进程** —— 客户现场不用教"每个新程序都要配一次"，也不会出现"忘了给某个 exe 加规则导致内网不通"。Proxifier 的主要投诉都在这（每个程序都要配，漏配就报错）。
2. **阻断是"明确拒绝"而不是超时** —— 我们回 RST，应用立刻收到拒绝（实测 2.3s）；纯丢弃会让业务卡 21s 才超时。
3. **诊断是产品化的** —— 一键诊断 + 规则模拟器 + 诊断包（别人要么没有，要么是给工程师用的独立工具）。
4. **一键装机** —— 装机包含程序/驱动/配置/启动脚本/说明/校验值；Proxifier 的企业下发要 license + 目录服务器那一套。
5. **一眼看清"为什么不走隧道"** —— 影子规则检测（含"被更宽网段整个包住"这种最常见的排序错误）、按最具体优先排序。

## 三、真缺口（有实际场景、值得补）

按"投入产出"排，★ 越多越值得：

| # | 缺口 | 场景（不补会怎样） | 谁有 | 成本 |
|---|---|---|---|---|
| **G1** | ★★★ **上游竞速（首个候选超时/失败后，并发试剩下的）** | 现在一条上游半死 → 业务等满 5s 才切换（已从 10s 降到 5s，但仍有等待）。竞速可以压到 ~1 个 RTT | gost `parallel` 策略 | 0.5～1 天（注意流量放大：只在"第一跳失败后"竞速更划算；gost 官方也建议节点 ≤2-3 个才用） |
| **G2** | ★★★ **DNS 走代理 / DNS 泄漏防护** | 客户内网名只能由内网 DNS 解析；域名一旦被系统 DNS 解析出去就是个泄漏面（我们目前只"检测"不"防"） | Proxifier（远程解析三模式 + 假 IP 子网） | 2～3 天（我们目标直接用 IP，域名靠 hosts，所以**先确认客户是否真有此需求**） |
| **G3** | ★★ **连接环路检测** | 与 Clash/其它代理共存时，理论上可能出现"我们的流量被 Clash 再送回我们"的环（Proxifier 专门做了这个开关） | Proxifier | 1 天（可以在连接表里加"同目标同链异常高频 / 源=目标"的启发式检测） |
| **G4** | ★★ **直连流量也纳入统计** | 现在直连连接只统计出方向（回来的包不经内核过滤器）。客户端问"到底省了多少流量"答不上 | Proxifier（Handle Direct Connections 把直连也纳入） | 1～2 天 |
| **G5** | ★★ **按网络接口绑定规则** | 笔记本在公司走隧道、回家必须直连；现在得手动改规则 | Proxifier | 1 天 |
| **G6** | ★★ **哈希策略（按客户端 IP / 目标 hash）** | 多个出口 IP 时，同一台机器每次都从不同出口出去，对方按 IP 做会话/白名单就会飘 | gost `hash` 策略 | 0.5 天 |
| **G7** | ★★ **配置加密 + 远程自动更新** | 装机包含明文口令（现在是靠"别外发"的纪律）；客户多了以后改配置要一台台跑 | Proxifier（profile 加密 + Web 自动更新） | 加密 0.5 天；远程更新要服务端，2～3 天 |
| **G8** | ★ **抓包 dump / 原始流量留存** | 疑难问题（比如业务说"某个操作就是不通"）时，抓一份原始流量比看日志有用得多 | Proxifier（.dmp） | 1～2 天（注意隐私与磁盘） |
| **G9** | ★ **上游传输扩展（ws/wss、gRPC、QUIC…）** | **取决于上游会不会换实现**（见第四节风险） | gost 一大堆 | 每个 1～3 天 |
| **G10** | ★ **两条 DNS/连接环路之外的安全性检查** | 例如"某内网网段既在隧道里又被系统代理覆盖"这类自相矛盾配置 —— 体检里现有的够用，但可以再补 | — | 0.5 天 |

## 四、结构性风险（比"缺功能"更重要）

1. **我们的上游 `socks5+tls` 是 gost 特有组合，不是业界标准。**
   gost 官方 FAQ 明确"v2 与 v3 除了功能相似外可以认为是全新应用"，只有标准协议（TLS/HTTP/SOCKS5）互通。
   一旦上游换成 v2ray/xray/sing-box/私有实现，我们现在的三条上游形态里 `socks5+tls` 会直接失效，
   只有 `socks5` / `http` 保底。
   → **建议**：把上游做成"适配器"（每种上游一个独立模块 + 各自的假上游回归测试），
   而不是在内核/引擎里堆 gost 私有分支。这项**应该在下次动上游代码时顺手做**（0.5 天，属于重构而非新功能）。
2. **UDP 是最大的架构性风险。** 我们只拦 TCP；如果上游改成 UDP 承载（hysteria2 / tuic / wireguard / kcp），
   我们连流量都截不到 —— 这不是"加个协议解析"能解决的，需要补 UDP 拦截 + UDP→上游 的转发链路。
   → **建议**：只做"架构预留"（把 relay 路径抽象成不假设 TCP），不实现。**除非**客户明确出现 UDP 业务需求。
3. **Proxifier 的进程维度我们永远不做**（见第五节）—— 这是有意取舍，不是能力缺失。

## 五、明确不做（附理由，免得以后翻来覆去讨论）

| 项 | 谁有 | 为什么不做 |
|---|---|---|
| 按进程/应用决定走不走代理 | Proxifier 核心 | 客户现场"每个新程序都要配一次"的成本 > 收益；按目标判定更省心 |
| UDP 中继 | gost 全面 | 内网业务全是 TCP；且上游侧限制多（gost 自己也说明 UDP dialer 只能配 ssu、UDP 通道只能用于第一跳） |
| 多跳串联（A→B→C） | gost hops | 现网是单跳；有多条上游已能满足"换路"需求 |
| TUN/TAP 组网、透明代理入站 | gost | 我们要的是"按目标分流"，不是"全局 VPN"；Windows 上 TUN 还要额外驱动（gost 官方也提 TAP 在 Windows 的坑） |
| Prometheus metrics / 插件体系 | gost | 客户环境没有监控系统可对接 |
| 域名/正则规则匹配 | Proxifier（通配符）/gost（正则） | 我们的目标是 IP/CIDR（内网直接给 IP）；域名靠 hosts 托管解决 |
| 限速/配额 | gost | 我们的定位是"通路"，不是"带宽管理设备" |
| 端口转发/反向隧道 | gost rtcp/rudp | 不在"客户机访问内网"这个场景里 |

## 六、结论（怎么用这份文档）

- **核心能力面已经齐了**：规则、动作、多上游、健康检查、观测、诊断、部署、装机 —— 客户现场要用的都有，且诊断/装机这两个"交付环节"比两个对手都强。
- **接下来最值得做的三件事**：G1 上游竞速（0.5～1 天，直接改善体感）、G3 环路检测（1 天，防最阴的坑）、G4 直连统计（1～2 天，回答"省了多少流量"）。
- **其次**：G5 接口绑定、G6 哈希策略（各 0.5～1 天，都是小活）。
- **要等需求**：G2 DNS 走代理（先问客户有没有内网域名解析需求）、G7 配置加密/远程更新（客户数量上来再说）、G8 抓包。
- **要等上游**：G9 传输扩展（先确认上游会不会换实现）。
- **该顺手做的重构**：上游适配器抽象（第四节风险 1）。
